# 云端 GPU 并发（fan-out）能力与实测边界

> 目标：把「一次拉起多台 GPU 并行跑」做成可复用的基础设施，而不是一次性脚本。
> 本轮（round 30）交付了发射器 + 载荷 + 并行审计，并拿到了**真实的边界数字**。

## 1. 组成

| 文件 | 作用 |
|---|---|
| [scripts/cloud_gpu_fanout.py](../scripts/cloud_gpu_fanout.py) | 并发发射器：N 个作业同时提交 → 统一轮询 → 全部取回 → 汇总（光子/耗时/GFLOPS 分布）。带成本硬门禁、持久化台账、超时保护、截止取消 |
| [cloud_gpu/gpu_bench.py](../cloud_gpu/gpu_bench.py) | 容器内载荷：GPU 身份/cuBLAS 预热/事件计时/FP32+FP16 matmul 吞吐/HBM 带宽/正确性校验（fp64 参考） |
| `runs/cloud_gpu/fanout*.json` | 每次 fan-out 的完整报告（含每个 job 的状态、光子、指标） |

用法：

```powershell
# 只算成本，不提交
.\.venv\Scripts\python.exe scripts\cloud_gpu_fanout.py --plan --jobs 8 --run-minutes 6 --wait-minutes 25
# 真跑（必须显式 --go；余额不足会被硬门禁拒绝）
.\.venv\Scripts\python.exe scripts\cloud_gpu_fanout.py --go --jobs 8 --run-minutes 6 --wait-minutes 25
```

## 2. 硬门禁（每一道都来自踩过的坑）

| 门 | 行为 |
|---|---|
| `--go` | 没有它只打印计划；不会创建任何作业 |
| 光子门 | 先算 `最坏情况光子数 = 目录价 × (run + wait) × 转换系数`，再与 `--max-photons` 比较；**余额读不到 → 直接拒绝**（绝不 fail-open），实测余额不足时确实拒绝 |
| 现金通道 | 提交固定 `--payment-source photon`；本账号现金余额 -0.09，永远不会被用到 |
| 持久台账 | 每次提交立即追加 `runs/cloud_gpu/submissions.jsonl`；重跑时已提交的 index 会被跳过，避免崩溃后重复扣费 |
| job id 解析 | 从混杂的输出里用正则取 id；**exit 0 但取不到 id → 整轮中止**（否则会出现"已扣费但没人管"的孤儿作业） |
| 截止取消 | 轮询超时后对仍存活的作业执行 `batchjob kill`，不让它继续计费 |
| 陈旧产物 | 每轮清空 `runs/cloud_gpu/job_*`，且只接受 **mtime 晚于本轮开始** 的结果文件 |

## 3. 并行审计发现的真实缺陷（已修）

这一轮用 4 个并行审计 agent 交叉审查发射器/载荷/安全，共抓出 10 个真缺陷，其中 4 个会**直接烧钱或让数字说谎**：

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | job id 解析遇到多段 JSON 就返回 `{}` | **已扣费的作业变成孤儿**（实测触发：`exit=0 job=None`） | 容错正则 + 无 id 即中止 |
| 2 | 光子门比较的是"余额 vs 常量"，且余额未知时跳过 | 空转风险（`jobs=2000` 也能过） | 换算成最坏情况光子数再比；未知即拒绝 |
| 3 | 计划里 `worst_wait = worst_run`，且没传 `--wait-minutes` | 最坏敞口**低估 2.6 倍** | 计划纳入真实等待上限 |
| 4 | 载荷计时在循环内 `cudaMalloc`、无预热、每次迭代同步 | **GFLOPS 系统性偏低，且越快卡越偏低** | 预分配 `out=`、预热、CUDA event |
| 5 | 未固定 TF32 / fp16 归约模式 | "fp32"可能其实是 TF32，数字虚高 | 显式关闭并记录 `math_mode` |
| 6 | 校验和与 GEMM 无关 | 跨卡一致性检查**形同虚设** | 确定性输入 + fp64 参考 + `max_rel_err` |
| 7 | 上传包包含 `__pycache__/*.pyc`（内含宿主路径 `D:\Dev\...`） | 泄漏开发机路径 | 上传改为白名单 |
| 8 | `--case` 可用绝对路径/`..` 逃出包目录 | 可读任意本地文件并回传到产物 | 解析后强制包含关系 |
| 9 | `apt-get` 无超时、无 noninteractive；`shell=True` 拼 `--install` | 卡死到作业超时 / 命令注入 | argv 调用 + 超时 + 非交互 |
| 10 | 失败作业的光子不计入总额 | 成本被系统性低估 | 汇总全部作业记录 |

## 4. 实测边界：光子是共享预算

这是本轮最重要的**运营事实**：

| 时间 | 光子余额 | 说明 |
|---|---|---|
| 22:47 | 25 067 | 初始 |
| 23:52 | 24 745 | H3 验收几个作业（多数 0，一个 5） |
| 01:00+ | **6** | **本会话自身的模型网关按量计费消耗了绝大部分**（账本条目：`Bohrium 模型网关按量结算（每份0.01元）`，单次 48-68 光子） |

换算基准（实测）：4090 跑 407 s ≈ **64 光子** → 约 **0.157 光子/秒**，或约 **95-103 光子/RMB 目录价**。
按此推算：

| 规模 | 最坏情况光子 | 当前余额 6 是否可行 |
|---|---|---|
| 1 × 4090，2 min run + 5 min wait | ~66 | ❌ |
| 8 × 4090，6 min run + 25 min wait | ~1 400 | ❌ |

**结论（诚实版）**：fan-out **机制可用、门禁正确、审计已收敛**；但**8 台 GPU 同时跑在光子余额 6 的情况下不可行**——门禁会（并且已经）拒绝。真要大并发，需要先充值光子，或把 agent 会话与 GPU 预算分开（本会话的推理费用本身就在消耗同一份光子）。

## 5. 本轮实际尝试（含失败，如实记录）

| 时间 | 动作 | 结果 |
|---|---|---|
| 03:10 | 用**修复前**的发射器提交 1 台 4090（`gpu-fanout-01`） | 提交 exit 0，但**job id 解析失败**（输出是多段 JSON）——**正是审计预测的"孤儿作业"缺陷，当场复现** |
| 03:10-03:23 | 该作业在队列里等待 | `status: failed`、`statusReason: **deadline_exceeded**`、`spendTime: 0`、`photonCost: 0` |

**结论**：4090 池在此时段不可调度（排队超过 `--max-wait-time 20m`）——这正是上游已知行为：
**排队失败不扣费，但也没有算力，不能记成"跑过"**。修复后的发射器新增：无 job id 即整轮中止、
截止时对存活作业执行 `kill`、结果文件必须晚于本轮开始。


## 5. 实测结果（round 30 第二轮，光子到位后）

### 5.1 单卡基准（c8_m32 × 1×4090，作业 `94f52564…`，32 s / 光子未结算即已完成）

| 指标 | 数值 |
|---|---|
| GPU | `NVIDIA GeForce RTX 4090`，驱动 580.95.05，46068 MiB，UUID `GPU-8d288ec1…` |
| 环境 | torch 2.13.0+cu126，CUDA 12.6，`allow_tf32=False`，`float32_matmul_precision=highest` |
| **FP32 GEMM** | **52 506 GFLOPS**（2048³，中位 0.327 ms，n=7，CV 0.6%） |
| **FP16 GEMM** | **137 307 GFLOPS**（中位 0.125 ms，n=7） |
| **HBM 拷贝** | **773 GB/s**（256 MiB，`copy_correct=True`） |
| 正确性 | 与 fp64 参考的 `max_rel_err` = 0.064（fp32 累加合理量级），`finite=True` |
| 卡状态 | 2520 MHz，采样前后 40 °C，功耗 88.7 W → 43.0 W |

对照 4090 规格（FP32 ~82.6 TFLOPS、FP16(fp32 累加) ~165 TFLOPS、HBM ~1008 GB/s）：
FP32 达到 **63.6%**、FP16 **83%**、带宽 **77%** —— 数量级与比例都合理，说明基准本身可信。

### 5.2 8 路并发（`run_id=20261110-124852`，`fanout_8x4090.json`）

| 指标 | 结果 |
|---|---|
| 提交 | **8/8，4.3 秒内全部提交成功**（并发提交确实并行） |
| 调度 | **3 succeeded / 5 deadline_exceeded**（4090 池部分可用，排队超 10 min 的自动失败） |
| 真跑到的 3 张卡 | fp32 = **52 541 / 52 603 / 52 686 GFLOPS** → **跨卡一致性 0.28%** |
| fp16 | 137 412 / 137 413 / 137 730 GFLOPS |
| 计算耗时 | 35 / 32 / 31 s（含 CUDA 初始化），总 wall 341 s |
| 光子 | 作业记录合计 **26**；同时段余额读数 10 003 → 9 994（**结算异步，两个读数都要保留**） |

**结论**：并发链路（提交→调度→运行→取回→汇总）**端到端可用**；同一 SKU 的多张 4090
吞吐**高度一致（0.28%）**，可以放心用于同构并行任务；瓶颈是**调度供给**，不是我们的代码。

### 5.3 并发时的调度现实（同一时段三个 SKU 同时探）

| SKU | 结果 |
|---|---|
| `c6_m32_1 × V100` | 一直 `unschedulable`（45 min 等待窗口内未排上） |
| `c8_m32_1 × 4090` | **约 20 秒内调度成功**（首个成功作业） |
| `c128_m512_8 × 8×L20` | 长时间 `pending`（未在窗口内排上） |

→ **不同 SKU 的可用性差异极大**；发射器支持 `--sku` 切换，应当在批量任务前先做 1 个作业的
"SKU 探测"，再决定用哪个池子放大。


### 5.4 两轮 8 路并发的累计结果（共 **6 次成功 GPU 运行**）

| 轮次 | 提交 | 成功 | 失败原因 | fp32 范围 (GFLOPS) | 跨卡一致性 | 校验和一致 |
|---|---|---|---|---|---|---|
| batch1 (`20261110-124852`) | 8/8 in 4.3 s | 3 | 5× `deadline_exceeded` | 52 542 – 52 686 | 0.28% | ✅ |
| batch2 (`batch2`) | 8/8 in 2.1 s | 3 | 5× `deadline_exceeded` | 52 449 – 52 619 | 0.32% | ✅ |

全部 6 次运行的汇总：

- **FP32**：52449 – 52686 GFLOPS（均值 52574）
- **FP16**：137202 – 138262 GFLOPS
- **输入校验和**：1 个不同值 → **完全相同**（同一确定性负载）
- 每次运行 31–35 s（含 CUDA 初始化），批次 wall 341 / 349 s
- 光子：batch1 记录 26、batch2 记录 0（结算滞后）；**余额仍在 9 990 量级，两批合计消耗 ≈ 13-40 光子**

**这意味着**：同构任务可以放心并行（吞吐一致性 0.3% 以内、输入完全一致、校验和可比）；
真正的不确定性在**调度供给**（两轮都是 8 提交 3 成功，失败者 0 光子 0 算力），
所以并发策略应是"**多提交 + 容错重试**"，而不是"精确提交 N 个然后假设全成功"。

### 5.5 批量任务的推荐配方（基于实测）

1. 先 1 个作业探 SKU（约 20-35 s 出结果，~9 光子）；
2. 按 **需求数量 × 2.5 左右** 提交（实测成功率 3/8 ≈ 37%，且失败不扣费）；
3. `--wait-minutes 15`：短了会大量 `deadline_exceeded`，长了只增加敞口（失败仍 0 费用）；
4. 汇总时看 `fp32_consistency_pct` 与 `checksums_match`，它们分别证明"吞吐一致"与"负载一致"。


### 5.6 单机多卡（2×L20，作业 `4eedc8f2…`，55 s / 27 光子）

| 指标 | 数值 |
|---|---|
| 设备 | `c32_m128_2 × 2 NVIDIA L20`（92 SM/卡） |
| 单卡 FP32 | **36 853 GFLOPS**（2048³，中位 0.466 ms，CV 0.29%） |
| 单卡 FP16 | **100 935 GFLOPS** |
| HBM 拷贝 | 618.6 GB/s（`copy_correct=True`） |
| 逐卡（多卡模式） | dev0 **36 850**、dev1 **36 893** GFLOPS（CV 0.2% / 0.4%） |
| **两卡同时算** | 聚合 **52 489 GFLOPS**，逐卡 31 328 / 31 008 → **缩放效率 84.2%** |
| 跨架构确定性 | `input_checksum = -364.5751452445984`，与 4090 那 6 次**完全相同** |

**这组数证明了三件事**：

1. 多卡载荷的计时是对的（逐卡 CV < 0.5%，两卡数值一致）；
2. **并发会互相拖慢**：单卡 36.9 → 同时跑时 31.0 TFLOPS（每卡 84%），聚合效率 84.2%——
   这是 PCIe/CPU 共享带来的真实代价，不是"线性加速"的幻觉；
3. 同一个确定性负载在不同架构（4090 / L20）上给出**逐位相同的输入校验和**，说明跨机型可比。

**修掉的缺陷**：第一版多卡计时把 CUDA event 记在"当前设备"（0 号）上却让矩阵乘跑在 1 号卡，
于是 dev1 报出 110 TFLOPS / CV 0.82 的假数；已改为每个设备都在 `torch.cuda.device(index)` 上下文里
建张量、记事件、同步，并新增静态回归测试 `tests/test_gpu_bench_multidevice.py`。

### 5.7 单机 8 卡：三次尝试，三次没排上

| 尝试 | 等待窗口 | 结果 |
|---|---|---|
| #1 `82386a20…` | 45 min | `scheduling_timeout`，0 光子 0 算力 |
| #2 `cea30560…` | 45 min | 一直 `job_submitted`，未排上 |
| #3 `35b099f4…` | 25 min | `scheduling_timeout`，0 光子 0 算力 |

**结论**：`c128_m512_8 × L20` 在这个账号的可达时段内**基本不可得**。多卡代码路径已经就绪并有
2 卡实测（缩放效率 84.2%），但 8 卡的数字**拿不到**——这属于供给侧限制，不是我们的缺陷。
规划并发时按「单机最多 2 卡可靠」来算。

## 6. 仍然未证明的

- 8 路并发下的**调度成功率**：本轮 1 台 4090 就在排队 10+ 分钟后 `deadline_exceeded`（0 光子、0 算力）；
  已知上游 `unschedulable` 是常态，真正的并发成功率需要光子充足时段复跑才能测；
- 多卡**同一模型**的 GFLOPS 一致性（需要 ≥2 次成功的 GPU 作业才有分布）；
- `--concurrency` 很高时 CLI 的限流行为。

这些都需要在光子充足后按同一套脚本复跑，报告结构已经就绪。

### 5.8 重要教训：**批次作业状态 ≠ 计算状态**（round 51）

60/80 Ha 的收敛作业在平台上都是 **`succeeded`**，但容器里两个 NWChem 计算实际是
**`MPI_ABORT ... out of heap memory`、exit 255**——因为结算看的是启动器脚本的退出码（0）。

**规则**：云端证据必须**同时**满足 ① 作业终态成功、② 输出里有**正常结束标记**
（NWChem 的 `Total times`）、③ 没有失败标记（`MPI_ABORT`/`out of heap memory`/`buffer overflow`）。
只满足 ① 的结论一律不采信。`cifkit.export.convergence.output_completed()` 负责这一判据，
`tests/test_output_completion.py` 锁住它。
